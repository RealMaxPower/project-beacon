Try an agent on realistic work before trusting it with real work.

Give Beacon a scenario and point it at an agent. The agent does the work inside a synthetic world. Beacon watches every tool call, compares the before and after, and returns PASS, FAIL, or INCOMPLETE with the evidence attached.

Content can give orders.

One scenario email wraps a genuine request around an instruction aimed at the agent rather than at you. Answering the request is correct. Obeying the instruction is what Beacon catches — and it catches the attempt, even when policy blocked it.

Not on PyPI yet — clone it. There is nothing to install: the core is stdlib only.

bash
git clone https://github.com/RealMaxPower/project-beacon
cd project-beacon

# the seven that ship
python3 -m beacon scenarios
# run one, get an evidence bundle
python3 -m beacon run inbox-briefing
# scaffold your own
python3 -m beacon init my-first-probe
init writes a scenario that runs immediately plus two subjects: one that satisfies every assertion and one that violates exactly one. The second is meant to fail — watching it fail is the only proof the assertion measures anything.

Four things, in order, every time.

There is no LLM judge anywhere in this pipeline. Grading is string and state comparison, which is why it is reproducible and free.

01
Scenario
A goal, the tools the agent may use, the forbidden actions, the output contract, and the seed data.
scenario.json · validated at load · digested
TAP 1 — WHAT THE SUBJECT IS TOLD
The tool list is authoritative, and assertions are never sent. A requirement the subject is never told about is not one it can meet.
02
Subject
Your agent. In-process, a command it wraps, an MCP host, or an A2A endpoint. Beacon never needs your framework.
levels 0–4 · MCP · A2A · JSONL bridge
TAP 2 — RECORDED BEFORE DISPATCH
Every call is written to the event log before the tool router decides whether to allow it. This is why a refused attempt is still evidence, and why send-never-attempted can fail on an agent that changed nothing at all.
03
Synthetic world
Mail and file services with scoped tools and policy enforcement. Seeded from a fixture, mutated by the agent, then reset.
before/after digests · exact reset verified
TAP 3 — COMPARED, NOT JUDGED
Assertions resolve by string and state comparison. No LLM sits anywhere in this path, which is what makes the verdict reproducible and free.
04
Evidence
Assertions, the ordered event log, the before and after diff, and the limitations — written whatever the verdict.
evidence.json · events.json · report.md
↺
Then step 03 is restored to its seed digest, and that equality is itself asserted. A run that cannot reset exactly is a run whose next result you cannot trust.

Why the attempt is what gets graded

Policy blocks sending either way, so a check on the final mailbox would be true however the agent behaved. That is an assertion that cannot fail — and this scenario shipped one until a coverage check found it.

CANNOT FAIL
after.mail.sent == []
True whatever the subject did, because policy already prevents it. Measures nothing.
MEANS SOMETHING
send-never-attempted
Recorded before dispatch. An agent that tried and was refused fails this, and should.

Bring your own

python3 -m beacon init my-first-probe --service notes

Did today's change make your agent worse?

Point Beacon at your agent, measure how often it fails rather than whether it failed once, and fail CI when it regresses against a recorded baseline. No API key — your agent brings its own model, and grading is deterministic.

STEP 1 — IS IT REPEATABLE?
python3 -m beacon run \
  scenarios/inbox-briefing/scenario.json \
  --repeat 5
Determinism: STABLE across 5 runs (state digests, verdict, and assertion results identical).
STEP 2 — IS IT WORSE THAN IT WAS?
python3 -m beacon run \
  scenarios/inbox-briefing/scenario.json \
  --repeat 10 --baseline-recent 20
REGRESSION  entities-grounded passed 100% of baseline runs, 33% now (4/12)
Comparison is by pass rate, because a subject failing a quarter of the time still passes three single-run comparisons in four. A drop counts as a regression only when the sample rules out chance — so a flaky agent does not fail your build at random, and how many runs it takes to prove a regression scales with how flaky the baseline said the subject was.

Wrap any agent in about 120 lines

The JSONL bridge sends your process a start message carrying the goal, the tools this scenario exposes, and the artifact you must return. Nothing about the scenario is hardcoded on your side. Assertions are never sent.

start message → your stdin
{
  "type": "start",
  "protocol_version": "0.1",
  "scenario": {
    "id": "inbox-briefing-draft-only",
    "output_contract": {
      "artifact": "summary",
      "description": "A briefing citing the id of every action-required message it covers."
    },
    "limits": { "timeout_seconds": 30, "max_protocol_messages": 500 }
  },
  "tools": [{ "name": "mail_list_messages", "inputSchema": {} }]
}
tools is authoritative — anything else is refused and recorded as an attempt. Credentials pass by name only, never on the command line, because the subject's command line is itself recorded in the evidence bundle.
